# WhaleYing Benchmark Lab — 开发规范

## 项目原则

以下四项原则长期有效，不受技术栈确认状态影响：

- **最小化**：只引入当前实际需要的代码、依赖和结构，不为未来可能的需求提前建设。
- **可复现**：实验和构建过程必须可在同等环境下重复执行并得到一致结果。
- **可验证**：每项评测结论必须有可追溯的数据支撑，不接受无来源的断言。
- **低成本**：在满足正确性的前提下，优先选择轻量方案，减少不必要的基础设施复杂度。

## 技术栈候选方案（待确认）

以下方案需经用户明确批准后方可执行安装、初始化或强制应用：

| 用途 | 候选工具 | 状态 |
|------|----------|------|
| 编程语言 | Python 3.10+ | 待确认 |
| 包管理 | uv 或 pip | 待确认 |
| 代码格式化 | black 或 ruff format | 待确认 |
| 代码检查 | ruff | 待确认 |
| 类型检查 | mypy | 待确认 |
| 测试框架 | pytest | 待确认 |

## 文件与目录命名

- 目录名：小写字母 + 下划线（`benchmark_runner`）
- Python 文件：小写字母 + 下划线（`memory_eval.py`）
- 实验配置文件：`<实验名>_config.yaml`（命名规则待确认）
- 结果文件：`<实验名>_<日期>_results.json`（命名规则待确认）

## 代码规范（候选，待技术栈确认后生效）

- 公开接口、核心评测逻辑及复杂函数应提供必要的类型注解和说明；简单、局部、语义明确的辅助函数不强制要求完整 docstring。
- 模块拆分依据职责单一性、可测试性和可维护性判断，不得仅为满足行数限制而拆分。
- 不引入未在项目正式采用的依赖管理机制中声明的依赖（具体工具和文件格式待技术栈确认）。
- 不在代码中硬编码模型名称、API Key 或路径；使用配置文件或环境变量。

## 提交规范

格式：`<类型>(<范围>): <简短描述>`

| 类型 | 适用场景 |
|------|----------|
| `feat` | 新增功能或评测能力 |
| `fix` | 修复错误 |
| `exp` | 新增或更新实验 |
| `data` | 数据集变更 |
| `docs` | 文档变更 |
| `refactor` | 重构（不改变行为） |
| `chore` | 构建、依赖等杂项 |

示例：`feat(memory-eval): 添加多跳记忆召回评测模块`

## 禁止事项

- 不得创建 Hooks、自定义 Agents、数据库或额外基础设施，除非经用户明确批准。
- 不得运行安装命令（`pip install`、`uv sync` 等），除非经用户明确批准。
- 不得自动生成测试文件，除非用户明确要求。
- 不得在未读取现有文件内容的情况下覆盖文件。
